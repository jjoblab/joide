## ADR-001 — Consommation de Forge : bibliothèque versionnée depuis mavenLocal (v0.2.24)

**Contexte.** Le cahier des charges (§4.2) impose de consommer Forge comme
**bibliothèque versionnée** via ses modules `api`, `json`, `client`, `setup`, sans
copier ni forker. Historique : aucune publication Maven n'existait en v0.2.6
(contournement d'abord par composite build, puis par `tools/forge-mavenlocal.sh`
qui injectait `maven-publish` par script d'initialisation sans toucher au checkout
épinglé).

**Décision (mise à jour du 2026-11-22).** Forge **v0.2.24** embarque `maven-publish`
sur ses cinq modules bibliothèque (`api`, `json`, `client`, `setup`, `engine`) :
la consommation devient `jo.forge:<module>:0.2.24` depuis `mavenLocal`, alimenté par
`./gradlew publishToMavenLocal` dans le dépôt Forge (demande F-01 livrée partie
locale). Le script `tools/forge-mavenlocal.sh` reste pour les checkouts anciens ;
la version vit dans `build-forge/build.gradle` (bump explicite, aucun `+`).

**Dépendances actives.** `jo.forge:{api,client,setup}:0.2.24` (+ `engine:0.2.24` en
test, moteur factice `--fake`). Apports de v0.2.13 → v0.2.24 activés d'office :
anti-recul du manifeste, réparation d'installation interrompue au démarrage, clé
de rotation, plafond de décompression en flux, AAR (F-05), ViewBinding (F-06),
composants aapt2/plateformes publiés (F-02).

**Risques.** mavenLocal reste local : la publication sur un dépôt public (JitPack,
GitHub Packages) reste la solution cible (F-01 partie ouverte). **Recommandation**
inchangée : version explicite, jamais de `+`.

## ADR-002 — Choix et changement de mode : assistant sans défaut, préférences versionnées

**Contexte.** §4.1 : au premier lancement, l'utilisateur choisit le mode (Forge ou
Gradle) sans choix caché par défaut ; le mode se change plus tard (installer, réparer,
désinstaller) ; chaque projet indique les modes compatibles.

**Options.**
1. Un « mode par défaut Forge » silencieux au premier lancement — rejeté : interdit.
2. Assistant plein écran à la première installation : pages de présentation des deux
   modes (apports, limites honnêtes, tailles et espace disque), choix explicite,
   installation immédiate du mode choisi.
3. Choix différé (« explorer d'abord ») — retarde l'installation, complique les états.

**Décision.** Option 2 : `AssistantModeFragment` (4 pages : bienvenue → Forge → Gradle →
confirmation du choix), tailles **constatées depuis le manifeste du canal Forge** et les
composants déclarés du mode Gradle (jamais inventées). État persisté dans `core-store`
(`modes.préférences` : mode préféré, mode installé, état d'installation). Le changement
de mode vit dans les paramètres (installer l'autre mode, réparer, désinstaller). Chaque
écran d'accueil de projet affiche un badge de compatibilité (détection §4.5).

**Risques.** Tailles affichées fausses si le manifeste change : mitigation par lecture
dynamique. **Recommandation** : ne jamais afficher une taille non constatée.

## ADR-003 — Distribution hors magasin

**Contexte.** Forge a établi (docs/distribution.md) que Google Play interdit à la fois le
téléchargement de code exécutable hors Play (politique « Device and Network Abuse ») et
un `targetSdk 28` en mise à jour. JoIDE a exactement la même architecture (coquille +
composants téléchargés) et le même `targetSdk 28`.

**Options.** 1. Play avec moteur embarqué : réécriture de l'architecture. 2. Hors
magasin : GitHub Releases + F-Droid éventuel. 3. Play avec `targetSdk` récent : briser
l'exécution des binaires téléchargés (mode Gradle impossible, Forge compromis).

**Décision.** Option 2 : APK signé (clé stable versionnée dans les secrets CI) publié en
GitHub Release ; la confiance repose sur la vérification de composants (manifeste signé
Forge, sommes SHA-256), jamais sur le canal. F-Droid : conditionnel (licence, build
reproductible) — non engagé.

**Risques.** Moindre visibilité ; mise à jour manuelle. **Recommandation** : écran
« À propos » avec canal de vérification de mise à jour.

## ADR-004 — Exécution de binaires et `targetSdk` (point §4.3.3)

**Contexte.** Depuis Android 10 (API 29), une application dont `targetSdk ≥ 29` ne peut
pas exécuter un binaire de son stockage inscriptible (politique W^X de SELinux) ;
`execve()` depuis `nativeLibraryDir` reste permis. Le mode Gradle exécute `java`,
`gradle`, `aapt2`, des outils du shell ; Forge exécute `aapt2` téléchargé. Forge a
tranché `targetSdk 28` pour sa coquille (D-04).

**Options.**
1. `targetSdk 28` pour JoIDE (les deux modes exécutent librement) — choix de Forge.
2. `targetSdk 33+` et **empaquetage des binaires en `.so`** dans `nativeLibraryDir`
   (extraction à l'installation) : le binaire `aapt2`/`java` du mode Gradle devient un
   `.so` renommé, exécutable ; le bootstrap lui-même reste des données.
3. `targetSdk 33+` avec `exec()` interdit : le mode Gradle ne peut pas exister en
   terminal réel.

**Décision.** Option 1 : **`targetSdk 28` confirmé** (avec ADR-009 pour le produit
entier). Cohérence totale avec Forge, terminaux couverts : Android 9+ ; les magasins
sont exclus (ADR-003, assumé). L'option 2 est **documentée comme plan de sortie** (si
un jour le magasin devenait requis) : le terminal et Forge savent où vivent leurs
binaires ; la bascule exigerait un empaquetage `.so` et la re-publication des
composants — coût estimé, non engagé.

**Risques.** « Cran de compatibilité » visible ; certaines APIs récentes
(toutes celles que l'UI voudrait utiliser au-delà de 28) : compensées par les
bibliothèques AndroidX (backports) et vérifiées par le contrôle API 28 (L0).
**Recommandation** : le contrôle API 28 doit être strict dès L0 (interdiction des
symboles non couverts sans version minimale AndroidX vérifiée).

## ADR-005 — Licences du terminal (point §4.3.1)

**Contexte.** L'application libre d'émulateur de terminal et sa bibliothèque de vue
sont GPLv3 ; les paquets du bootstrap ont des licences variées ; le packaging du
propriétaire (`codeide-packages`) fournit déjà un bootstrap à préfixe dédié. Le détail
complet est dans `licences.md` §1.

**Options.**
1. Consommer l'application Termux **installée séparément** (l'utilisateur l'installe
   lui-même) : zéro obligation GPL, expérience fragmentée — rejeté par le cahier des
   charges (terminal **intégré**).
2. Fork **dans ce dépôt**, module `build-gradle` isolé, exécution dans un processus
   séparé : obligations GPL assumées (sources publiées, notices, écran À propos).
3. Réécriture complète d'un terminal (nécessite émulateur VT-100/xterm complet) :
   coût de développement énorme, qualité moindre.

**Décision.** Option 2 : fork dans ce dépôt sous `jo.joide.terminal.*`, module
`build-gradle`, processus séparé, notices (`LICENSE-TERMINAL.md`,
`NOTICE-PAQUETS.md`), écran À propos exhaustif. **Le reste de JoIDE
(Apache-2.0) ne lie pas contre le module GPL** (communication par intents et processus,
pas par classes) ; l'analyse « arm's length » est dans `licences.md` §1.1.

**Risques.** Le risque de propagation GPL est le point critique : mitigé par la
frontière processus + l'isolement module. Toute évolution qui ferait entrer une classe
du fork dans `app-android` doit être refusée en revue. **Recommandation** : règle de
revue explicite + contrôle de dépendances (le graphe l'interdit).

## ADR-006 — Préfixe et bootstrap (point §4.3.2)

**Contexte.** Le bootstrap officiel de la famille libre est construit pour le préfixe
`/data/data/com.termux/files/usr` : les binaires y ont des chemins codés en dur
(interp : `#!/data/data/com.termux/files/usr/bin/sh`). Le packaging du propriétaire
fournit un bootstrap **au préfixe de JoIDE** déjà (paquets natifs reconstruits avec
l'identité du paquet dédié — constat README de `codeide-packages` : « natively
compiled with the jo.codeide package identity »).

**Options.**
1. **Bootstrap reconstruit au préfixe de JoIDE** (base : le packaging du propriétaire) :
   binaires natifs arm64 (pas de traduction), chemins corrects, compatibilité paquets.
   Coût : reconstruction de la chaîne (elle existe déjà), maintenance du miroir de
   paquets. Taille : ~80-100 Mo minimum pour le minimal + JDK.
2. **Rootfs via proot** : distributions complètes (Debian…) au prix d'une couche de
   traduction d'appels (coût performance, surtout I/O et `fork`), mais les paquets
   sont standards. Taille : plus grande ; perf : médiocre pour Gradle (spawn de
   processus fréquents).
3. **Mixte** : proot pour l'outillage exotique, natif pour la chaîne de build.

**Décision.** Option 1 (bootstrap natif à préfixe propre, base `codeide-packages`) :
Gradle et le JDK veulent des performances de `fork`/`exec` correctes — proot les
dégrade notablement. L'option 3 est documentée comme suite possible (outils exotiques
sous proot à côté du minimal natif).

**Risques.** Maintenance du miroir de paquets (assumée, elle existe déjà) ;
compatibilité des paquets : seul le périmètre minimal (bash, coreutils, dpkg,
gzip, tar, git) est engagé en L6, le reste viendra de la demande des utilisateurs.
**Recommandation** : plafonner strictement le périmètre initial du bootstrap.

## ADR-007 — Processus fantômes et services de premier plan (point §4.3.4)

**Contexte.** Android 12+ tue les processus d'arrière-plan d'applications ciblant des
API récentes (phantom process killer / frozen states), en particulier les enfants
multiples d'une application (cas du terminal : une session = un fork de shell). Apps
ciblant API 31+ voient la limite `MAX_PHANTOM_PROCESSES` et leurs enfants tués ;
l'application Termux historique documente ce combat (l'utilisateur doit désactiver
« PhantomProcessKilling » par ADB sur certains constructeurs).

**Options.**
1. `targetSdk 28` (notre choix, ADR-004) : le tueur ne s'applique pas de la même
   manière — les mécanismes d'Android 12 visent le plus les applications récentes ;
   Android 14+ : les vérifications se durcissent globalement. Même avec 28, le terminal
   **doit** se déclarer service de premier plan : c'est le contrat.
2. Service de premier plan avec notification persistante + type `specialUse` ou
   `connectedDevice` (Android 14 impose une déclaration) : le terminal vit
   publiquement tant qu'une session est ouverte.
3. Masquer la notification : rejeté (anti-contrat Android, et vulnerable au tueur).

**Décision.** Option 2 : service de premier plan **notification visible** tant qu'au
moins une session est ouverte ; arrêt du service quand la dernière session est fermée
(la persistance « application en arrière-plan » du cahier des charges §4.3 = service
FG + notification, pas un process caché). Sur Android 12+ un appareil ciblant nos
cibles : vérification appareil réel consignée (§4 de limites). Chaque session de
terminal est un enfant du service, jamais du processus UI (§4.7 du cahier des
charges : un crash du terminal ne tue pas l'interface).

**Risques.** Certains constructeurs tuent malgré tout (contrats d'énergie) : la
documentation utilisateur (« paramètres constructeur ») sera livrée à L8.
**Recommandation** : afficher le compteur de sessions dans la notification.

## ADR-008 — Diagnostics Gradle : sortie parse + script d'initialisation (point §4.4)

**Contexte.** En mode Gradle, la Console et la section Problèmes doivent être
alimentées comme en mode Forge. Gradle n'a pas d'API de diagnostic standard pour les
tâches externes ; il imprime des diagnostics de compilation par le plugin Android
sur stdout/stderr dans un format quasi-stable.

**Options.**
1. **Parse de la sortie** (`--console=plain`, locale fixe `C`, regex de
   `FAILURE: …/… file:line:col`) : simple, capte le succès/échec, les messages
   texte, les positions.
2. **Script d'initialisation** (`-I outil.gradle`) injecté par JoIDE :
   `BuildListener`/`TaskExecutionListener` → JSON sur un fichier de événements :
   progression par tâche, durées, états — données structurées fiables.
3. **Outil custom dans `init.d`** + Tooling API : la Tooling API (client embarqué)
   est la voie « propre » mais exige d'héberger l'API dans l'environnement (poids).

**Décision.** Option **1 + 2 combinées** : le script d'initialisation fournit la
**progression et les états de tâches** (données structurées fiables, sans parsing),
le parse de sortie couvre les **diagnostics de compilation** (fichier/ligne) que le
listener ne donne pas. Limites consignées : le script d'init est fragile aux
changement de Gradle (version épinglée de l'environnement, contrôlée par nous) ;
les diagnostics du plugin Android restent un format semi-stable (évolution à
suivre par version de AGP ; l'épinglage AGP (ADR conception §1) maîtrise le risque).

**Risques.** Gradle écrit le script dans le terminal process (processus séparé) ; la
deuxième exécution doit le remplacer proprement (atomicité). **Recommandation** :
toujours écrire le script avant chaque build, jamais le réutiliser entre versions.

## ADR-009 — `targetSdk 28` confirmé pour l'application

**Contexte.** Le cahier des charges (§0, §3) : « targetSdk 28 par défaut (à confirmer ou
infirmer par ADR, voir 4.3) ». ADR-004 a établi la contrainte W^X. L'UI (Material 3,
AndroidX récent) veut des APIs modernes, toutes fournies en backport par les
bibliothèques AndroidX (pas par le `targetSdk`).

**Options.** 1. `targetSdk 28` (cohérence Forge, exécution libre des binaires).
2. `targetSdk 33+` (UI moderne, binaires empaquetés `.so` uniquement — complique tout
le mode Gradle). 3. Split : coquille moderne + terminal ciblant 28 : impossible (un
seul `targetSdk` par application).

**Décision.** Option 1 : **confirmé**. `minSdk 28`, `targetSdk 28`, `compileSdk 35`
(les bibliothèques AndroidX modernes se compilent contre le dernier SDK). Contrôle
automatique : la tâche `verifierApi28` (L0) vérifie que tout symbole Android utilisé
existe à l'API 28 (analyse du bytecode contre `android-28`) ou est couvert par la
desugaring/librairies (liste d'exclusions tenue à jour, revue par version).

**Risques.** Comportements d'ancienne plateforme (permissions implicites) : la
défense est le refus des permissions non nécessaires (JoIDE n'utilise ni stockage
partagé ni localisation ; SAF only). **Recommandation** : n'inclure que des
permissions strictement requises dans le manifeste (L0 : deux permissions, dont
`FOREGROUND_SERVICE` et `INTERNET`).

## ADR-010 — SDK Android : licences, redistribution, binaires arm64 (point §4.3.6)

**Contexte.** Le mode Gradle a besoin de plateformes (`android.jar`),
build-tools/aapt2 (arm64), et l'utilisateur doit accepter les licences du SDK.

**Options.**
1. **Redistribuer** nous-mêmes les composants du SDK : les Terms n'autorisent pas la
   redistribution générale (sauf composants explicitement Apache-2.0) — la position
   de Forge (docs/distribution.md §7 : garde juridique, garde-fou avant publication)
   est la nôtre.
2. **Télécharger depuis la source officielle** (`dl.google.com`, URLs du dépôt Maven
   Google pour aapt2 et des repository XML pour les plateformes) avec somme SHA-256
   épinglée dans notre manifeste : l'utilisateur accepte la licence **dans JoIDE**
   avant le téléchargement, le composant arrive vérifié. Pas de redistribution par
   nous : nous distribuons des URL et des sommes, pas des binaires.

**Décision.** Option 2 : écran « Licences du SDK » (acceptation **par l'utilisateur**,
avant tout téléchargement — le contrat), composants téléchargés depuis les serveurs de
l'éditeur, sommes épinglées (vérification intégrité). Le `aapt2` **arm64 natif** : la
version Maven est `aapt2-<version>-linux.jar` (binaire x86_64 encapsulé) — inutilisable
sur téléphone ; la source **constatée** pour arm64 : la chaîne du propriétaire
(`codeide-tools`, CMake — binaire déjà produit pour l'écosystème maison ; intégration à
L6 par lecture de ce dépôt). Un `aapt2` Android arm64 peut aussi être construit depuis
AOSP (forge a le même besoin, F-02).

**Risques.** URLs officielles changeantes : mitigé par manifeste versionné +
diagnostic de repli. **Recommandation** : afficher la source de chaque composant à
l'installation (transparence).

## ADR-011 — Intégrité des composants du mode Gradle (point §4.3.8)

**Contexte.** Tout composant téléchargé (bootstrap, JDK, Gradle, SDK) doit être vérifié
SHA-256 + manifeste signé, comme Forge. Forge possède déjà : module `setup`
(`CanalMoteur` : manifeste + signature ECDSA vérifiés contre une clé épinglée,
téléchargement repreneur, extraction anti-traversée, installation atomique).

**Options.** 1. Réutiliser le module `setup` de Forge comme bibliothèque versionnée
(notre mode de consommation Forge, ADR-001) : manifeste signé par la **même clé que le
moteur Forge** (canal unique). 2. Réécrire notre propre chaîne : duplication.
3. Manifeste non signé (sommes seules) : plus faible (attaque de mise à jour du
   manifeste).

**Décision.** Option 1 : le manifeste des composants du mode Gradle est **produit par
nous, signé avec une clé JoIDE dédiée** (ECDSA P-256, même mécanisme `OutilManifeste`
de Forge — la clé publique JoIDE est épinglée dans l'application). La **signature du
manifeste Forge reste celle de Forge** : deux canaux distincts, deux clés, un même
vérificateur (module `setup`). L'extraction d'archives utilise l'extracteur anti-
traversée de `setup` pour tous les composants Gradle (bootstrap, JDK zips, SDK zips).

**Risques.** Clé privée : jeton CI, jamais versionnée (comme Forge).
**Recommandation** : la clé de signature du manifeste JoIDE vit dans les secrets CI
dès L6 ; la rotation de clé est documentée (version de manifeste + nouvelle clé
épinglée avec double période de grâce).

## ADR-012 — Mémoire : Gradle sans daemon (point §4.3.5)

**Contexte.** Un téléphone a 8-16 Go de RAM partagés ; le daemon Gradle par défaut
prend un tas de 512 Mo-2 Go et survit aux builds ; Android 12+ tue agressivement les
processus d'arrière-plan (ADR-007) ; l'UI doit rester vivante (cahier des charges
§4.7 : les travaux lourds hors du processus UI — déjà le cas : Gradle tourne dans le
processus terminal).

**Options.**
1. **Daemon avec tas borné** (`-Xmx512m` configurable) : builds incrémentaux plus
   rapides après le premier ; coût : ~512 Mo-1 Go de RAM permanente occupée pendant
   la session ; vulnérable au tueur sous pression mémoire (le daemon est tué, Gradle
   redémarre de zéro).
2. **Sans daemon** (`--no-daemon`, fork unique par build) : mémoire rendue à chaque
   fin de build ; chaque build paie le coût de démarrage (~2-5 s) ; prévisible.
3. Daemon « à durée de vie courte » (`org.gradle.daemon.idletimeout` bas) :
   compromis intermédiaire.

**Décision.** Option 2 par défaut : **`--no-daemon`** avec tas du daemon unique réglé à
512 Mo (`org.gradle.jvmargs=-Xmx512m` dans les propriétés Gradle du projet utilisateur)
— la prévisibilité prime sur l'incrémental ; l'option 3 livrée comme réglage
avancé (paramètres mode Gradle, « garder le daemon vivant : plus rapide, plus de
mémoire »). Sur pression mémoire (`onTrimMemory` critique) : arrêt du daemon s'il
existe, journal de l'événement dans le journal des écroulements.

**Risques.** Premier build lent (~2-3 min sur matériel récent) : l'écran
d'installation du mode Gradle et la Console affichent honnêtement l'attente
(progress par tâches, ADR-008). **Recommandation** : indicateur mémoire (barre
d'état discrète dans les paramètres du mode).

## ADR-013 — Stockage des projets : privé par défaut (point §4.3.7)

**Contexte.** §4.3.7 et §4.6 : emplacement des projets (privé vs partagé), liens
symboliques, permissions, accès du terminal.

**Options.**
1. **Stockage privé** (`filesDir/projects/`) : aucun scope de stockage à demander
   (compat 28 : le privé est toujours accessible), données protégées par le sandbox
   de l'app ; inconvénient : inaccessible aux autres applications et à MTP
   (l'utilisateur ne « voit » pas ses fichiers sans JoIDE).
2. Stockage partagé (SAF/dossier scoped) : visible MTP ; exige une permission de
   gestion de fichiers sur Android récent ; antivirus/MediaScanner l'indexent (le
   build produit des milliers de fichiers) ; risque de perte (les nettoyeurs de
   stockage suppriment « les caches »).
3. Mixte : privé par défaut + export/import SAF ponctuels.

**Décision.** Option 3 : privé par défaut (`filesDir/projects/<slug>`), export/import
par SAF (aucune permission de stockage au manifeste). Le **terminal** (mode Gradle)
accède aux projets via le **préfixe** (ADR-006 : le bootstrap est installé dans
`filesDir/gradle-env/usr`, le chemin des projets est un sous-répertoire du
stockage privé de la même application — le shell les voit comme des fichiers
ordinaires). Les **liens symboliques** : interdits à l'intérieur des projets
(comme Forge D-12 : refus avec diagnostic, jamais d'ignorance silencieuse) ;
autorisés dans l'environnement du préfixe (livrés par le packaging des paquets).

**Risques.** L'utilisateur « ne retrouve pas » ses fichiers : l'écran À propos et
les fiches projet documentent l'emplacement ; l'export SAF couvre le besoin de
sauvegarde. **Recommandation** : bouton « exporter le projet » dès L4.

## ADR-014 — Registre de fournisseurs LLM : vérification documentaire préalable (Lot 2)

**Contexte.** La refonte IA remplace les identifiants de maquette (« laboratoire »,
« passerelle ») par des fournisseurs réels. La règle du dépôt interdit d'envoyer un
champ non confirmé ; les erreurs de câblage (URL, paramètre) coûtent des tours
perdus et des messages trompeurs.

**Options.** 1. Câbler tout fournisseur « connu » de mémoire. 2. Entrer au registre
uniquement ce qui est vérifié dans la documentation officielle du fournisseur, avec
la source citée dans `ProviderSpec`. 3. Un adaptateur par fournisseur natif.

**Décision.** Option 2 : `ProviderRegistry` (OpenRouter, OpenAI, Gemini — couche de
compatibilité OpenAI vérifiée dans la doc Google : base
`…/v1beta/openai/`, Bearer, streaming et outils —, passerelle personnalisable).
Chaque URL et chaque champ de requête (objet `reasoning` OpenRouter, `provider.*`
de routage, `X-Title`) est cité depuis la documentation officielle. **Anthropic
différé** : sa documentation officielle est inaccessible depuis l'environnement de
développement (blocage par région) et les sources tierces se contredisent ;
l'adaptateur entrera au registre après vérification — la page Fournisseurs ne
l'affiche pas entre-temps (jamais de fournisseur fantôme).

**Risques.** Base URL qui évolue : la source est citée dans le `ProviderSpec` et
l'ADR ; le bouton « Tester la connexion » (Lot 7) détecte le problème en un appui.

## ADR-015 — Codec JSON et lecteur SSE internes : zéro dépendance dans le module `ai` (Lot 1)

**Contexte.** Le module `ai` est du Java pur sans dépendance runtime (politique de
licences). L'analyse JSON par `indexOf` a coûté des pertes de caractères (guillemets
échappés, sauts de ligne, points de code Unicode) ; le découpage SSE à la main
cassait sur les commentaires, le CRLF et l'UTF-8 coupé entre deux lectures.

**Options.** 1. Ajouter une bibliothèque JSON (org.json, Gson, Jackson). 2. Codec
interne complet (parseur + écrivain, positions d'erreur) et lecteur SSE incrémental.
3. Réparer les `indexOf`.

**Décision.** Option 2 : `ai/json/Json` (objets, tableaux, échappements complets,
nombres, erreurs avec position, Java 8 strict) et `SseParser` (lignes découpées au
niveau octet — un caractère multi-octets UTF-8 ne contient jamais `0x0A` —, décodage
par ligne complète, commentaires ignorés, CRLF, données multi-lignes). Les réponses
d'erreur HTTP sont rédigées par `Secrets.redact` avant tout affichage.

**Risques.** Cas JSON exotiques : le corpus de tests couvre échappements, imbrication
profonde, nombres, invalides ; une limite rencontrée se corrige dans le codec (un
seul endroit).

## ADR-016 — Conversations à double contenu, schéma versionné (Lot 4)

**Contexte.** Le transcript vu par l'utilisateur et l'historique exact vu par le
modèle (appels et résultats d'outils) divergent : rejouer une conversation ne
redonnait pas le même contexte au modèle ; changer de fournisseur ou de modèle
perdait la conversation.

**Options.** 1. Rejouer le transcript seul (perte du contexte d'outils). 2. Double
contenu persisté (messages + historique exact), schéma versionné avec migration à
la lecture. 3. Historique seul (transcript dérivé, appels d'outils visibles en
brut — illisible).

**Décision.** Option 2 : `Conversation` v2 (transcript + historique exact archivés,
fournisseur/modèle/effort épinglés, usage cumulé) ; `ConversationStore.JsonFiles`
écrit atomiquement, ignore les corrompus avec avertissement, migre les fichiers v1
(transcript seul → historique de départ). Emplacements séparés : assistant
`filesDir/assistant/`, agent `filesDir/agent/<empreinte-projet>/` (SHA-256 du
chemin — un projet, ses conversations).

**Risques.** Taille des fichiers : l'historique exact croît ; le compactage
`ConversationHistory` (hystérésis, REF-113) borne ce qui est envoyé, la persistance
reste complète. Corruption : fichier ignoré, jamais une liste vide muette.

## ADR-017 — Rendu Markdown maison, streaming-safe (Lot 5)

**Contexte.** Les réponses du modèle arrivent en flux : un rendu qui ne tolère pas
les préfixes (fence non fermée, emphase ouverte) clignote ou lève des exceptions ;
le format comporte des conventions propres à l'atelier (bloc ```suivi, blocs de
code avec cible `title="chemin"`, diffs unifiés).

**Options.** 1. Bibliothèque Markdown (Markwon) côté app : dépendance + re-rendu
complet à chaque delta. 2. Parseur maison en blocs, tolérant aux préfixes,
interprétation (raisonnement, propositions, diffs, commandes) en amont du rendu.
3. Texte brut.

**Décision.** Option 2 : `MarkdownParser` (blocs typés ; pour tout préfixe d'un
document, aucun exception et un arbre provisoire correct — propriété testée pas à
pas) + `ResponseInterpreter` pur (raisonnement `<think>` à part, bloc ```suivi →
propositions, nature des blocs de code, nettoyage hors des blocs). Le rendu Android
assemble des vues par bloc ; les boutons Copier/Appliquer/Ouvrir vivent sur les
cartes de code.

**Risques.** Couverture Markdown : le corpus de tests couvre les constructions
réelles des modèles ; une construction manquante se rend en paragraphe (correct,
jamais cassé). Markwon resterait possible pour un rendu enrichi — la dépendance
n'est pas justifiée aujourd'hui.

## ADR-018 — Réglages IA : matrice de câblage vérifiée en CI (Lot 7)

**Contexte.** Les réglages IA étaient persistés mais jamais lus (diagnostic de la
mission) : des contrôles morts affichés comme réels.

**Options.** 1. Confiance dans la revue. 2. Matrice documentée (docs/analyse-ia.md)
+ contrôle automatique (tools/check-cablage-ia.sh) qui échoue si une clé n'a pas
d'écrivain ou de lecteur ; les réglages non câblés se disent « à venir » à l'écran
ET dans la matrice. 3. Tout supprimer jusqu'à câblage complet.

**Décision.** Option 2, ajoutée à la CI (ci.yml, à côté de check-langue et
check-deps). État actuel : 12 clés câblées (fournisseur, modèle, URL passerelle,
effort, plafonds, mode de permission, attribution et routage OpenRouter), 2 clés
« à venir » annoncées (recherche web, serveur MCP — l'outillage n'existe pas), 1
drapeau interne de migration.

**Risques.** Un lecteur purement cosmétique (initialiser un switch) satisfait le
contrôle : la revue de la matrice reste obligatoire pour la sémantique ; le contrôle
garantit le plancher (aucune clé lue nulle part).

## ADR-019 — Jeu d'icônes d'arborescence original (Lot 2 tiroir)

**Contexte.** La refonte du tiroir gauche affiche une icône par type d'entrée
(convention visuelle des arborescences d'IDE : classe, interface, layout,
manifest…). Les jeux d'icônes des IDE existants ne sont pas réutilisables sans
examen de licence (celui de l'IDE de référence est explicitement fermé).

**Options.** 1. Bibliothèque d'icônes tierce : couverture partielle des types
métier (manifest, res/values), licence à auditer par icône. 2. Dessins
originaux en VectorDrawable : une puce colorée par catégorie (jetons
colors.xml, clair + sombre) et un glyphe géométrique par type. 3. Icônes
texte (lettre dans un carré) sans vectoriel.

**Décision.** Option 2 : 24 icônes `ic_tree_*` + décorations (points git,
pastilles de diagnostic), toutes écrites pour JoIDE — chemins vectoriels
originaux, aucune reprise de tracé existant. La convention visuelle (un
glyphe par type de fichier, dossiers en couleur primaire) est une idée, pas
un dessin : les idées ne se licencient pas, les tracés si. La classification
vit dans core-files (`FileKinds`) — l'UI ne connaît ni extension ni nom de
fichier, seulement des types et des drawables.

**Risques.** Lisibilité à 18 dp : les glyphes sont simples (lettres pleines,
formes géométriques) et testés sur les deux thèmes via les jetons ; un type
peu lisible se corrige en éditant un seul drawable, le mapping type →
drawable étant centralisé dans l'onglet Fichiers.
